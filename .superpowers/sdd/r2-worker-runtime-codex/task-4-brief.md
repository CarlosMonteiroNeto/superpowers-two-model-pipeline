### Task 4: Enforce separate Codex and OpenCode role policies

**Summary:** Package the three worker roles for both backends and enforce their command/edit boundaries with deterministic policy builders and hooks.

**Dependencies:** Tasks 1 and 3 are approved. Do not change their interfaces or add runtime dispatch from this task.

**Files:** Use the exact production and controller-owned test paths listed for Task 4 in `.superpowers/sdd/plans/r2-worker-runtime-codex.md`.

**Interfaces:**

- `codex_policy.build_overrides(role, runtime, request) -> list[str]`
- `codex_policy.check_tool_call(event, policy) -> dict`, using Codex's documented `PreToolUse` decision shape
- `codex_policy.capture_protected_state(request) -> dict`
- `opencode_policy.build_settings(role, runtime, request) -> dict`

## Controller rulings

1. The R2 canonical plan and design spec are the acceptance authority. This brief resolves fixture shapes only; it does not expand the policy scope.
2. `runtime` uses R1's validated structure: `backend`, and `roles[role]` with explicit `model`, backend-specific `settings`, `policy`, and `instruction`. Do not infer a model, effort, agent, or backend.
3. Codex `request` requires the packaged `developer_instructions` string and a `capabilities` object containing booleans `hooks_enabled`, `hooks_trusted`, `sandbox_enforced`, `bash_hook_covered`, `apply_patch_hook_covered`; lists `unhooked_mutating_tools`, `managed_policy_conflicts`, and `inherited_instruction_conflicts`. Missing, false, or non-empty safety facts that are required for the selected role raise `PolicyUnavailable`; do not weaken policy, mutate config, or silently continue.
4. Codex per-invocation argv uses documented options only: `--model`, `--sandbox`, `--ask-for-approval never`, and repeated `--config key=value`. Use `developer_instructions`, `model_reasoning_effort`, `agents.enabled=false`, `features.apps=false`, and `web_search="disabled"` as documented config keys. Operator gets `workspace-write`; reviewer and director get `read-only`. Director disables `features.shell_tool` and `features.unified_exec`. Never include `--yolo`, `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-bypass-hook-trust`, `--full-auto`, or an OpenCode-specific `--agent`/`--variant` flag. Do not modify user, managed, global, project, or installed-plugin config as a side effect.
5. Codex `check_tool_call` accepts the documented hook event object: `hook_event_name`, canonical `tool_name`, and `tool_input.command` for Bash/apply_patch. Unified exec is delivered as the Bash hook path. Reject malformed or unknown tool/input shapes. Return `hookSpecificOutput` with `hookEventName: "PreToolUse"`, `permissionDecision: "allow"|"deny"`, and a reason on deny.
6. Codex policy contains trusted supervisor inputs only: `role`, absolute `workspace_root`, `task_id`, `attempt_id`, task `touches`, `new_test_files`, `protected_paths`, exact `runner_commands` entries (`argv` and `cwd`), exact `read_only_commands`, `supervisor_path_grants`, and `director_approved_existing_changes`. Reject a tool event with shell chaining, redirection, pipes, command substitution, wrappers/expressions (`bash -c`, `sh -c`, Python `-c`, PowerShell `-Command`, generic `cmd /c`), direct Git commands, or any command not an exact approved runner/read-only descriptor. Do not allow an appended command after a safe prefix.
7. `apply_patch` parsing accepts only documented patch command text and authorizes every target path. Normalize `/` and `\\`, resolve relative paths against the workspace, and reject traversal, absolute paths outside the workspace, unknown patch directives, missing target paths, and any protected path. A supervisor grant must match path + task + attempt and issuer `supervisor`; an existing-file exception must match path + task + attempt and issuer `director`. Event-supplied grants never count. Protected plan, ledger, runtime and Git state cannot be granted.
8. The Codex hook wrapper `scripts/codex-policy` reads one JSON event from stdin and an attempt-bound policy via `PIPELINE_ROLE_POLICY`. It emits the documented hook decision as JSON. Missing policy, invalid JSON, invalid policy, or unavailable policy returns a deny. `codex/hooks.json` covers the documented `Bash` and `apply_patch` matchers; its definition is non-managed and requires explicit user trust. Setup reports that requirement and never auto-trusts or passes a hook-trust bypass flag. Hooks are workflow guards; OS sandbox and integrity checks are the security boundary.
9. `capture_protected_state` returns `version`, `workspace_root`, `task_id`, `attempt_id`, `git_head`, `git_status_sha256`, `protected_files`, and `fingerprint`. `protected_files` maps each normalized relative path to `{exists, sha256}`; a missing file has `exists: false` and `sha256: null`. Hash each requested file, capture the repository HEAD and porcelain status without mutating Git, and bind the fingerprint to workspace/task/attempt plus the file hashes. Record no file contents or credentials. Re-capturing after a protected file changes must yield a different fingerprint.
10. OpenCode builder returns `{ "config": ..., "capabilities": {"enforced": [...], "unsupported": [...], "available": bool} }`. It emits OpenCode's own role/permission configuration, using `model`, `variant`, `agent`, and the native permission keys for `read`, `edit`, `glob`, `grep`, `list`, `bash`, `task`, `external_directory`, `webfetch`, and `websearch`. Do not emit Codex TOML/CLI keys or assume live permission enforcement from a generated object. Default-deny unneeded tools; allow only scoped paths and exact declared runner/read-only commands. Protected paths receive a final deny rule. Unsupported required capabilities make `available` false and are enumerated; do not claim unsupported controls as enforced.
11. Role markdown remains English. Codex operator preserves RED/GREEN, self-review, TEST_DEFECT/escalation and scoped runner duties; reviewer returns an independent structured verdict and cannot edit or run tests; director returns bounded proposals and has no shell. Every role skips recursive brainstorming, self-update, tier questions, and manual subagent orchestration. Review the semantic instructions manually; tests verify packaging/transport through the runtime consumer instead of grepping prose.
