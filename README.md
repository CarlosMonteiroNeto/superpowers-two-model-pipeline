# superpowers (two-model-pipeline fork) — modified skills

Source: [`obra/superpowers`](https://github.com/obra/superpowers/tree/main/skills) (MIT), skills as of this fork's clone date.

Each of the 14 original skills was kept intact and given a **"Pipeline Integration"** section inserted right after its title, applying the principles from `README-LLM.md` (the `two-model-sdd-pipeline` / `flutter-app-pipeline` harness):

- **LLMs reason, scripts decide** — every checkable judgment call this skill used to leave to the LLM is pointed at the deterministic script/exit-code that now owns it (`route-next`, `red-gate`, `green-gate`, `final-gate`, `doc-check`, `run-gates`).
- **Fixed four-role engine** — Script A (deterministic loop owner), B (strategist), C (`two-model-coder`, write-only, Operational), D (`two-model-reviewer`, Strategic). `subagent-driven-development`'s SKILL.md carries the full role-mapping table.
- **Structured verdicts, not prose** — review-related skills (`requesting-code-review`, `receiving-code-review`) now route on D's fixed JSON shape (APPROVED / SEND_BACK / ESCALATE) instead of free-text comments.
- **State is external** — plan.json + git + JSONL ledger, never conversational memory; this is what makes every loop resumable after compaction.
- **Cache-aware, logged dispatch** — all subagent calls go through `scripts/dispatch --agent NAME [--continue SESSION]`, never inline/ad-hoc prompts.
- **RTK compression + Graphify-before-LLM** — large outputs (logs, diffs, JSON reports) get minified via `token-kill`/`cmd` before hitting context; dependency context comes from `graphify-subgraph`, not manual grepping.
- **English-only artifacts** — specs, briefs, ADRs, ledger summaries, commit messages, skill files: English regardless of the developer's language. The only exception anywhere in the pipeline is user-facing UI copy.

## Update: closed the post-round-1 automation gap (two-model-sdd-pipeline)

Verified against the actual scripts, not just the docs: after round 1's
script-driven Coder dispatch, **nothing in the reference implementation ever
called `green-gate`**, and `orchestrator`'s `CODER*`/`REVIEW*` cases were
no-op stubs that just handed control back to B — meaning every retry round,
every gate check, every commit, and every Reviewer dispatch after round 1
silently required B to do it by hand, despite all of it being mechanical
(git diff + a gate exit code + a session id already on disk). `README-LLM.md`
and `SKILL.md` described a "script-autonomous loop" that the scripts didn't
actually implement.

Fixed with one new script and two edits, tested end-to-end against a fake
repo + a stubbed `opencode` binary (round 1 fails, fix round resumes with
`--continue` and passes, commits, and — separately — a `TEST_DEFECT` log
correctly short-circuits to `escalated` with no further retries):

- **`skills/two-model-sdd-pipeline/scripts/coder-gate`** (new): runs after
  every Coder round, decides PASS/FAIL/TEST_DEFECT/budget-exhausted purely
  from the gate's exit code and the round's log content, ledgers
  `coder_round` (and `escalated` on TEST_DEFECT), builds each fix round's
  prompt as plain file-path interpolation (prior diff + gate report + brief
  — the same content `coder-prompt.md`'s Round 2+ section already
  documented, now actually generated by a script instead of by B), and
  redispatches C with `--continue`. On green: commits (generic engine) or
  defers to `green-gate`'s own commit (Flutter), then builds the review
  package and dispatches D.
- **`red-gate`** (both Flutter and generic): now ledgers the `red_check`
  entry it was missing, then chains straight into `coder-gate` instead of
  stopping at "C dispatched" — one `orchestrator` call now runs a task from
  RED to reviewed-and-committed (or genuinely stuck) without returning to B.
- **`orchestrator`**: `CODER*` now actually calls `coder-gate` (for a
  resumed/interrupted session — the normal path never reaches this case);
  `REVIEW*` stays a status passthrough since the Reviewer dispatch already
  happened inside `coder-gate`/`green-gate`.

## Update: subagent-driven-development audit (prompts/scripts consistency)

Auditing the single-session skill against the new RED-at-brief-time paradigm surfaced three real gaps, now fixed:

- **`SKILL.md` "Handle the report"** still said implementers report one of *four* statuses — `implementer-prompt.md` already reports five (added `TEST_DEFECT`). Added the missing **TEST_DEFECT** handling: correct the test or the brief yourself, re-verify RED, re-dispatch the same agent — never ask the implementer to fix its own test.
- **No tamper check before review.** The reviewer had no deterministic signal that a RED test file was touched — it depended on manually noticing it mid-diff-read. Added **`scripts/test-integrity BASE HEAD TEST_FILE...`** (mirrors `two-model-sdd-pipeline`'s `red-integrity`): byte-compares the named RED test files across the implementer's commit range, exit 1 on any change. Wired into step 3 ("Review the task") before the reviewer is dispatched, and into the fix loop's re-review (a fix round can tamper a test as easily as round 1 can).
- Confirmed clean: `implementer-prompt.md`'s five template placeholders (`[MODEL]`, `[BRIEF_FILE]`, `[RED_TEST_PATHS]`, `[REPORT_FILE]`, `[directory]`) all match what `SKILL.md`'s dispatch section fills in; `task-reviewer-prompt.md`/`re-review-prompt.md` make no test-authorship assumptions that needed correcting; `scripts/task-brief`/`review-package`/`sdd-workspace` needed no changes — they're already brief/diff plumbing, agnostic to who wrote which file.

## Update: script-decided routing (no LLM approval for scriptable checks)

New principle, stated explicitly in `README-LLM.md`: **if a check can be scripted, the script performs it and routes to the next step itself** — including the choice of *which* check/script to run, not just the check's pass/fail verdict. Concretely:

- **`skills/two-model-sdd-pipeline/scripts/resolve-toolchain`** (new): one-time-per-branch detection of the project's test/analyze commands from ecosystem markers (`pubspec.yaml`, `Cargo.toml`, `go.mod`, `package.json`, `pyproject.toml`/`requirements.txt`). Chains straight into `ledger-append` on success. A human is asked only when it exits ambiguous (1) or unknown (2) — that fallback is recorded too, so it's never asked twice on the same branch.
- **`skills/two-model-sdd-pipeline/scripts/red-gate`** (new): the generic engine's own RED-materialize-and-verify gate, previously only a documented placeholder — the generic (non-Flutter) loop had no way to reach `CODER` before this. Mirrors the Flutter fork's `red-gate` but reads `TEST_CMD` from `resolve-toolchain`'s ledger entry instead of hardcoding `flutter test`.
- **`orchestrator`** (updated): picks Flutter's `red-gate` or the new generic one by reading `gate.lang` from the ledger — a script decision, not an LLM guess.
- **`README-LLM.md` and `agent/flutter-pipeline.md`** (updated): the old "ask, once per branch, for the test + analyze commands" language is replaced by "resolve automatically; ask only on genuine ambiguity" — including for Flutter itself, which previously asked even though `pubspec.yaml` already makes the answer unambiguous.

## Update: real pipeline skills + RED-test paradigm fix

- **`skills/two-model-sdd-pipeline/`** and **`skills/flutter-app-pipeline/`** are included verbatim (SKILL.md, `scripts/`, `tests/`) from [`CarlosMonteiroNeto/superpowers-two-model-pipeline`](https://github.com/CarlosMonteiroNeto/superpowers-two-model-pipeline), so the "Pipeline Integration" notes in the other 14 skills point at scripts that actually exist in this package.
- **`agent/`** carries the four tier definitions (`flutter-pipeline`, `two-model-coder`, `two-model-controller`, `two-model-reviewer`) those scripts dispatch against.
- **`subagent-driven-development/implementer-prompt.md` was rewritten**: in this paradigm, RED tests are written by the controller/B *at brief-creation time*, verified failing for the expected reason, and only then handed to the implementer/C as read-only input. The subagent no longer writes, edits, or "adjusts" any test file — it implements against tests it did not author, and reports **TEST_DEFECT** (instead of silently fixing the test) if one looks wrong. `SKILL.md`'s dispatch checklist and process diagram were updated to match; `coder-prompt.md` in `two-model-sdd-pipeline/` already encoded this rule and was left as-is.

## What did NOT change

- The human-approval **HARD-GATE** in `brainstorming` — no script replaces a human "yes" on scope/design.
- Each skill's core technique (spike/bounded/architectural classification, TDD red/green discipline, systematic-debugging's phases, worktree mechanics, etc.) — the modification is integration, not a rewrite of the underlying method.
